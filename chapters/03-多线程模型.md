# 03 · 多线程：UI、Raster、Worker 与 CSP

三端共享同一套线程模型：UI 树保持单线程；GPU 操作归专用 Raster；后台纯计算用 WorkerPool；CSP 长连接每客户端一条通信线程。线程之间不共享可变状态，只靠「不可变快照 + 有界队列」交接。

## 3.1 四类线程的 ownership

| 线程 | 独占对象与工作 |
|---|---|
| **Platform / UI（当前共用）** | 平台事件、Widget/Element/State/View、字体排版与字形生成、TextureStore 单例、Canvas 构建、语义树与平台通道 |
| **Raster（每个 Compositor 一条）** | Renderer、全部 Vulkan 对象、纹理副本、RGBA/mip 转换、顶点和纹理上传、录制/提交/呈现 |
| **Worker（共享池默认 1~4 条）** | 值消息上的纯计算；不能访问 UI 树、字体单例、纹理单例或 Vulkan |
| **CSP（每个客户端一条）** | socket/poll、协议解析、FID 合并；只发布不可变行情快照 |

## 3.2 帧交接：两槽非阻塞流水线

1. **UI 线程 · Compositor::renderFrame** — 构建 Canvas（CPU 顶点流），把纹理脏矩形复制进帧
2. **FramePipeline · 两个槽循环复用** — Raster 提交 N 时，UI 构建 N+1；槽满就保留绘制请求，下一 VSync 取最新状态
3. **Raster 线程 · Renderer** — 按序消费快照：上传 → 录制 → 提交 Vulkan 命令 → present

- **不等待 GPU**：槽位占满只延后，不阻塞 UI 线程；
- **不积压历史帧**：无界队列不存在，旧几何在 resize 后会被跳过；
- **不提前清脏标记**：纹理增量按序应用，防止丢字形；
- **背压的精确语义**：Raster 侧等 fence 超时 16ms（一个 VSync 周期）或 acquire 返回 TIMEOUT/NOT_READY 时，render() 返回 Retry——绘制请求保留到下一次 VSync 取最新 UI 状态重试，同时 Raster 能返回队列响应 stop（vulkan_renderer.cpp:454-476）
- **kMaxFramesInFlight = 2 的对应关系**：顶点缓冲、命令缓冲、imageAvailable/renderFinished 信号量、fence 全部按帧槽各备一套，CPU 最多领先 GPU 两帧（vulkan_renderer.cpp:165、:304、:327）
- **纹理快照**：Raster 用自己的纹理原图副本，UI 可以继续写 atlas，Raster 不会读到一半更新的像素；副本也支持上传失败重试。代价是一份额外 CPU 纹理内存与在途帧脏区快照。

> **⚠️ 销毁顺序**：Surface 销毁：先停 VSync、清除 FrameFunc → 销毁 Compositor（停止接帧、舍弃排队几何、等待在执行的 Raster 及 GPU 清理完成）→ 才释放 IPlatform / 原生窗口。新 Compositor 首帧完整发送纹理，即使 UI 脏标记已清除。

## 3.3 WorkerPool：值消息计算

**完整用法（worker_pool.h）**

```cpp
// 作为 State 成员保存，dispose() 中 cancel()；不能作为临时值丢弃。
evk::WorkerTask task_;

void startCalculation(std::vector<float> input) {
    task_ = evk::WorkerPool::instance().compute(
        std::move(input),
        +[](std::vector<float> values) {   // work：普通函数或无捕获 lambda
            for (auto& value : values) value *= 2;
            return values;
        },
        [this](std::vector<float> result) {  // 完成回调只在 UI 线程执行
            setState([&] { values_ = std::move(result); });
        },
        [this](std::exception_ptr error) { /* UI 上处理失败 */ });
    if (!task_) { /* 等待队列已满（默认上限 64），可稍后重试 */ }
}

void dispose() override { task_.cancel(); }
```

- 输入/结果支持移动所有权（vector、unique_ptr）；API 拒绝顶层裸指针/引用；
- work 不得经全局变量绕过约定；不要让 work 反过来等 UI；不要在线程池里睡眠计时；
- WorkerTask 析构、替换、cancel 都会抑制未执行计算与未交付回调；已运行的计算自然结束，不强行中断；
- 多线程完成顺序不保证与提交一致；同一业务目标发新请求时替换旧句柄即可抑制旧结果；
- dispose 后即使结果已排入 UI 队列，也不会再调用捕获 this 的回调——取消句柄与 State 生命周期在 UI 串行操作。

## 3.4 postUi：后台线程进入 UI 线程的唯一入口

```cpp
postUi([this] {
    if (!mounted()) return;        // 迟到数据的第一道防线
    setState([this] { loaded_ = true; });
});
```

投递时自动 requestRender；任务在**下一次 beginFrame 开头**执行，任务中的 setState 可在同一帧进入构建和绘制。

## 3.5 CSP 通信线程：不可变快照

CspClient 拥有独立通信线程，内部是 poll() 事件循环：连接（多线路竞速）、认证、订阅全在这条线程完成；脏数据按最小 16ms 间隔合帧，不是每来一笔就发布。publish() 把整份状态拷进新的 CspMarketState，revision + 1，以 `shared_ptr<const CspMarketState>` 原子替换 latest——**旧快照永远有效**，UI 拿着它想读多久读多久。

> **ℹ️ UI 怎么知道数据变了？** 不 Interrupt、不直接 emit（EventBus 只在 UI 线程操作）。桥接用每帧动画回调轮询 revision：变了就取新快照、广播事件。等价于 Flutter setState 的合并语义——一帧内无论来多少笔行情，UI 最多重建一次。

## 3.6 观测：FrameMetrics 与 FrameTiming

- `FrameMetrics::instance().snapshot()` 可从任意线程读取最近成功帧、累计成功帧数、队列满导致的延后次数；
- FrameTiming 记录 UI 任务、动画、同步重建、布局、绘制、纹理快照、排队、Raster、顶点上传的 CPU 毫秒耗时，日志 `[evk][render][frame_timing ...]` 首帧及每 120 个成功帧输出一次；
- 阶段存在包含关系（Raster 包含等待 fence/acquire/present），不能把所有字段相加当成 GPU 执行时间。
